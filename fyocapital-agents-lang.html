00Contexto

Cómo leer este documento

Es el plano técnico de la implementación LangChain: baja a código la visión del documento conceptual (FYO-04, los cuatro agentes y la capa de riesgo). Cada pieza lleva una etiqueta de estado.

La unidad agéntica de fyoCapital convive en tres implementaciones que comparten los mismos scripts de datos: subagentes de Claude Code (en prueba), agentes CMA en platform.claude.com (operativo), y esta — LangChain local, scaffold v1. Las tres leen la misma data en vivo de OneDrive. La implementación LangChain es la candidata a sistema productivo porque es la única donde la orquestación es código propio: un grafo explícito que se puede versionar, testear, desplegar como API y extender con memoria y guardrails estructurales.

Cada componente del documento lleva una de tres etiquetas: hoy existe y corre en Langchain_Agents/; esperado está definido y es el próximo paso concreto; horizonte depende de decisiones de negocio que exceden esta carpeta.

La regla que hereda todo el documento

Informar vs. asesorar sigue siendo la línea. Nada de lo que se arma acá ejecuta una operación ni habla con el cliente final. Los agentes proponen con fuente y fecha; el comercial humano decide. La arquitectura técnica codifica ese principio: el guardrail no es un párrafo del prompt, es un nodo del grafo.

El loop ReAct de cada especialista es el mismo para los tres: el modelo recibe system prompt + conversación, decide si llama una tool o responde; si llama, el resultado JSON vuelve como tool message y el loop repite hasta que el modelo produce la respuesta final. LangChain 1.x lo implementa sobre LangGraph con create_agent — no hay código de loop propio que mantener.

Limitación 01

La memoria muere con el proceso

El REPL acumula historial en una lista de Python. Cerraste la terminal, no pasó nada: no hay checkpointer, no hay thread_id, no hay ayer. El supervisor tampoco persiste sus findings entre corridas.

Limitación 02

Guardrails solo en el prompt

Las reglas duras («B/C + pesos agresivo no va en primera», «todo número con fuente+fecha») viven en el system prompt. Se cumplen casi siempre — pero nada estructural las garantiza. No hay nodo de riesgo.

Limitación 03

Delegación secuencial

El supervisor delega de a una tarea por vuelta. Si la pregunta necesita comercial y research a la vez, van en serie aunque sean independientes. Con 5 delegaciones máximo, cada vuelta cuenta.

Limitación 04

Observabilidad artesanal

El trace se imprime en consola: delegaciones y tool calls. No hay LangSmith, no hay evals, no hay métricas. Comparar contra las otras dos implementaciones (PROBAR.md) es hoy un ejercicio manual.

02Los que ya corren

Los tres especialistas, paso a paso

Para cada uno: qué hace, el flujo interno numerado, y el tablero de encendido — cuándo prende, cuándo no y a quién deriva. El tablero es la parte que más importa: un agente que contesta lo que no le toca contamina a los otros.

Especialista · el cerebro hoy

Agente de Research

La house view consultable y citable. No conoce clientes ni carteras: es la fuente contra la que los otros dos verifican. Su regla existencial: nunca opina por su cuenta — todo sale del corpus, y cero hits se dice explícito («sin view vigente»), no se rellena.

01
Clasifica la consulta. Ticker puntual, varios tickers, tema libre o pulso de mercado. Cada forma mapea a un flag distinto de la tool: ticker / tickers / query / since.
02
Consulta el corpus. consultar_research busca sobre los 3 corpus: view_mercado.json (Mesa Capitales), qa_semanales.json (Mesa Granos) y consultoras_research.json (Delphos). Filtra por fuente con source si el usuario nombró una.
03
Sintetiza con trazabilidad. Cada número que cita lleva fuente + fecha: (view FyO 17/07), (Delphos Semanal 17/07). Tickers y views (BUY/HOLD/BULLISH) se citan directo del corpus.Regla dura: nunca cita un número que venga solo de un campo justificacion/detalle — eso es titular, no data.
04
Modo señal para briefings. Cuando otro agente le pide señal para los tickers del mix de un cliente, devuelve SOLO JSON tipado — {ticker, view, recommendation, drivers[], fuente, fecha} — sin prosa. Es el contrato máquina-a-máquina del «research al revés».
05
Declara el vacío. Cero hits en el corpus → «sin view vigente en el corpus para X». La ausencia de view es información: le dice al de Portafolio que recomiende sin el número, no que lo invente.

Que cada portafolio esté bien parado según el cliente y según el mercado. Diagnostica, recomienda con argumento trazable y prioriza. El argumento sin fuente no sirve — y propone, nunca ejecuta.

03Orquestación

El supervisor: el grafo que orquesta

Un StateGraph explícito de LangGraph. No es un prompt que «coordina»: es un grafo con nodos, aristas condicionales y estado tipado. Acá está el corazón técnico de la implementación — y el lugar donde se enchufan todas las piezas esperadas.

Topología actual del grafo · supervisor.py START ──▶ supervisor ──┬──▶ research ──▶ supervisor (vuelve con hallazgo)
                        ├──▶ comercial ──▶ supervisor
                        ├──▶ portafolio ──▶ supervisor
                        └──▶ finish ──▶ END

estado: messages · next_agent · task · findings[] · trace[] · delegations
tope: MAX_DELEGACIONES = 5 → síntesis forzada con lo que haya, sin inventar
Orquestador · una decisión por vuelta hoy

El turno del supervisor, paso a paso

El nodo supervisor decide un solo próximo paso por vuelta: delegar o finalizar. La decisión sale como structured output (Pydantic), no como texto libre — el grafo rutea sobre un campo tipado, no sobre una interpretación.

01
Arma el contexto. A la conversación del usuario le agrega los hallazgos acumulados: «HALLAZGOS DE ESPECIALISTAS PARA ESTA CONSULTA» con tarea delegada y resultado de cada vuelta anterior. Primera vuelta: «todavía no hay hallazgos».
02
Decide con schema. El modelo responde una SupervisorDecision: next_agent ∈ {research, comercial, portafolio, finish}, task (solo al delegar, autosuficiente y concreta) o final_answer (solo al finalizar).Reglas del prompt: para datos de negocio siempre delega; respeta dependencias (tenencias primero, research de esos tickers después); no repite delegaciones resueltas; si falta identificar un cliente, finaliza con una pregunta clara.
03
Ejecuta al especialista. El nodo del especialista corre su agente ReAct completo con la task como mensaje de usuario. El especialista usa sus tools las veces que necesite y devuelve su respuesta final.
04
Acumula y registra. La respuesta entra a findings (agente, tarea, resultado); cada tool call del especialista entra al trace. El flujo vuelve al supervisor, que ahora decide con más evidencia — y puede encadenar una tarea dependiente.
05
Sintetiza o corta. Con evidencia suficiente → finish: integra hallazgos, conserva fuentes/fechas y distingue qué propone el sistema de qué decide el humano. Si llegó a 5 delegaciones → síntesis forzada: responde con lo disponible, marca lo que quedó sin resolver, no inventa.
Prende cuando
  • La pregunta cruza dominios «qué tiene X y qué dice research de eso»
  • Una tarea depende del resultado de otra → encadena
  • Hace falta una respuesta única integrada de varios especialistas
No prende — sobra
  • Pregunta 100% de un dominio → el especialista directo es más barato y rápido
  • Falta identificar al cliente → finaliza preguntando, no delega a ciegas
  • Ya delegó lo mismo → no repite; sintetiza
Decisión: structured output Pydantic — ruteo tipado Anti-loop: MAX_DELEGACIONES=5 + síntesis forzada Esperado: checkpointer · delegación paralela (Send) · interrupt() para confirmación humana · gate de riesgo antes de finish
Por qué esta pieza es la que escala

Todo lo esperado del documento conceptual tiene un lugar natural en este grafo: el gate de riesgo es un nodo entre la propuesta y el finish; la memoria es un nodo de retrieve al inicio y un write al final; el orquestador del briefing a tres manos es exactamente este supervisor con delegación paralela; el human-in-the-loop es interrupt() nativo de LangGraph con checkpointer. No hay que rediseñar: hay que agregar nodos.

04Definición · esperado

Los que faltan en el grafo

Cuatro piezas definidas y aún no implementadas en LangChain. Tres ya existen como subagentes en la implementación Claude Code — portarlas es replicar prompt + tools. La cuarta, el gate de riesgo, es la única que cambia la topología del grafo.

Transversal · nivel exposición de fyo · el control esperado

Agente de Riesgo — el gate del grafo

Los cuatro agentes miran hacia afuera: buscan clientes, detectan señales, proponen operaciones. Ninguno sabe decir que no. Este es el único que mira hacia adentro —a lo que fyo está dispuesto a asumir— y su propósito es que el «no» llegue antes de la propuesta, no después. En LangGraph no es un hermano más: es un nodo obligatorio entre la propuesta y la salida — propuesta → riesgo → finish. Estructural, no discursivo.

01
Posición de riesgo online. La exposición de fyoCapital consolidada y viva: por cliente, instrumento, contraparte y vencimiento. Es el espejo del MCP de posiciones, pero mirado desde fyo y no desde el cliente. Hoy el armado es manual y la posición integrada no se ve.Es el cimiento: sin esta función las otras cuatro no existen. Y es la que define si esto son tres semanas o tres meses — la respuesta depende de si la posición y el saldo están en sistema o en planilla.
02
Chequeo previo — el guardrail. Antes de que el Comercial o el de Portafolio propongan, consultan: ¿este cliente puede? ¿esta operación entra en su perfil? ¿queda dentro de los límites de fyo? Respuesta binaria, con motivo. No opina: responde.No es un agente conversando con otro. Es un contrato: una pregunta, una respuesta, trazable. En el grafo son las dos caras de la misma función: el nodo gate (automático, antes del finish) y la tool chequear(cliente, operación) → veredicto tipado, consultable por cualquier especialista.
03
Simulador. La misma información con el framing invertido: el comercial pregunta «si hago este negocio, ¿qué pasa con la posición?» y lo ve antes de comprometerse.Es lo que hace que el guardrail se lea como servicio y no como policía. Por eso va como MVP. Técnicamente es gratis: la misma función del gate, expuesta como tool de solo lectura sobre la posición proyectada.
04
Centinela de límites y consola de excepciones. Alerta por exceso, concentración, desvío de plazo u operación fuera de perfil. Y la contracara, que es la que gana al analista: el «sí, pero» trazable, con aprobador y con fecha.Hoy las excepciones existen y no se ven en ningún lado. Hacerlas visibles vale tanto como los bloqueos. En LangGraph la excepción ES un interrupt(): el grafo se pausa, el aprobador aprueba con nombre y fecha, y todo queda persistido en el checkpoint — la consola sale sola del historial de interrupts.
05
Post-mortem. Qué se aprobó, qué se excepcionó y qué salió mal. Sin esto es un semáforo; con esto es lo que recalibra con mora real y alimenta la capa de datos del área de Riesgos.Es el principio «que aprenda», aplicado al riesgo: la mora real entra como reward al loop del cap. 09 (recalibra umbrales) y como aristas al cerebro del cap. 10 (la historia de cada excepción).
Prende cuando
  • Cualquier propuesta de portafolio va a salir → gate automático
  • «Si hago este negocio, ¿qué pasa con la posición?» → simulador
  • «¿Qué tan concentrado está X / el libro?» «¿quién opera apalancado?» → posición online
  • «¿Qué queda expuesto si sube el dólar / la tasa?» → estrés con drivers de la view
  • Un exceso o una operación fuera de perfil → centinela + excepción con interrupt()
No prende — frontera dura
  • Recomendar instrumentos → portafolio; este solo audita
  • Opinar de mercado → research; consume política escrita, no house view
  • Hablar con el cliente final — nunca, bajo ninguna forma
  • Evaluar al comercial — evalúa la exposición, no a la persona
Consume: la política de riesgo escrita — no la house view Entrega: el límite, el motivo y la excepción trazable Ya existe como: subagente riesgos-fyo en Claude Code MVP: posición online + simulador — primero de los cuatro a portar
Especialista · el vigía esperado

Agente de Competencia

Cómo viene fyo en volumen contra los otros ALyCs en cada mercado (BYMA, A3, MAV, MAE), con los rankings públicos de participación. Cosecha informes por web con confirmación antes de guardar; consulta el histórico local con fuente+fecha y marca VENCIDO lo que superó la cadencia. Prende ante «¿cómo venimos en BYMA?», «¿qué share tiene X?». No prende para nada que toque clientes, carteras o data no pública. En el grafo: especialista aparte con tools propias de harvest+consulta — cuarta fuente del cerebro, mira hacia afuera.

Especialista · el idóneo teórico esperado

Agente de Onboarding

Explica el mercado de capitales completo en lenguaje llano — bonos, ONs, CEDEARs, cauciones, TIR, duration, licitaciones, normativa — con ejemplos ilustrativos y sin recomendar nada. Prende ante «¿qué es X?», «explicame Y», material didáctico para el productor agro o el junior. No prende para opinar de mercado, mirar clientes ni citar tasas vigentes; ante «¿me conviene?» deriva al asesor. En el grafo: especialista sin tools de datos — solo conocimiento, cero riesgo regulatorio. El más barato de portar.

Cara al cliente horizonte

fyoCapital AI — otro grafo, no otro nodo

La cara al cliente NO entra en este grafo interno: es un grafo separado con superficie mínima — MCP de posiciones + research en modo lectura — y sus cuatro modos (informar → avisar → conversar → ejecutar). Compartir el proceso con los agentes internos sería mezclar audiencias con permisos distintos: el aislamiento es de arquitectura, no de prompt. Se para sobre el mismo cerebro de datos, con vista recortada.

Regla de portado

Orden: riesgo → onboarding → competencia

Riesgo primero porque cambia la topología (el gate tiene que existir antes de que el sistema proponga en serio). Onboarding segundo porque es gratis en riesgo y suma adopción. Competencia tercero porque requiere pipeline de harvest con confirmación humana — más piezas móviles. fyoCapital AI recién con el cerebro maduro y la decisión regulatoria tomada.

05La capa de datos

Del archivo suelto al MCP de FyO Digital

Hoy los agentes leen archivos: un CSV de tenencias y JSONs en OneDrive. El MCP de FyO Digital ya existe —34 herramientas sobre el CRM y la operación en vivo— y es el primer paso real del «MCP de posiciones» del documento conceptual: un contrato de datos estable en lugar de archivos que alguien regenera a mano.

El problema del archivo suelto no es que sea archivo: es que no es un contrato. El CSV de tenencias cambia de columnas y nadie avisa; quien ve el archivo ve todo (no hay permisos por usuario); la «foto de hoy» es en realidad la foto de la última regeneración; y el acceso por subprocess suma timeout de 60 segundos y parseo de stdout. El MCP invierte cada uno de esos puntos: herramientas tipadas con schema, autenticación por usuario con permisos del CRM, y el dato del sistema de origen en el momento exacto de la pregunta.

Contrato de datos · servidor claude.ai › Fyo Digital existe conexión LangChain esperada

El MCP FyO Digital: qué trae, hoy

34 herramientas, todas de solo lectura excepto una (guardar_resumen_minutas). Casi todo empieza en buscar_empresas: de ahí salen idEmpresa, CUIT y grupo económico — los identificadores que necesita el resto.

01
Identidad operativa. buscar_empresas resuelve la empresa por nombre y devuelve idEmpresa, CUIT, grupo económico y el comercial responsable por línea de servicio — «¿qué comercial lleva a X?» se contesta directo de acá.
02
Posición de plata, hoy. obtener_comitentes_fyocapital (la única que usa CUIT, como entero sin guiones) → obtener_saldo_fyocapital: el saldo del cliente en FyO Capital del día. Dato volátil: se cita siempre con fecha.
03
La operación. Contratos (rango máx. 365 días), órdenes «a precio» / «a fijar», cupos y solicitudes (máx. 90 días), potencialidad por campaña vigente y presupuesto/cumplimiento por grupo económico.Esta es la puerta al mundo Granos e insumos — el dato que el embedded del doc conceptual va a necesitar cuando sea decisión.
04
La relación. Contactos con área y seniority; minutas de reuniones con búsqueda por contenido. Es la data cualitativa que el doc conceptual daba por faltante — y la materia prima del debrief y del cerebro de datos (cap. 10).
05
La única escritura. guardar_resumen_minutas. En LangGraph esa llamada va SIEMPRE detrás de un interrupt(): resumen propuesto → OK del comercial → escritura. El debrief automático, con el humano en el medio por diseño y no por costumbre.
El MCP prende cuando
  • «¿Qué comercial lleva a X?» / contactos → buscar_empresas · contactos
  • «¿Qué saldo tiene X hoy?» → comitentes + saldo, citado con fecha
  • Contratos, órdenes, cupos, potencialidad, presupuesto → operación en vivo
  • «¿Qué se habló con X?» / guardar el resumen → minutas (escritura con interrupt)
No prende — sigue en las skills
  • Scores NBA, churn, wallet gap, arquetipos → artefactos analíticos locales
  • Tenencias por instrumento → CSV, hasta que el MCP las exponga
  • Research y views → corpus local (y después, el grafo)
  • Escribir sin confirmación humana — nunca
34 herramientas · solo lectura salvo guardar_resumen_minutas Integración: langchain-mcp-adapters — cada herramienta MCP = tool nativa del especialista Entornos: DEV · STG · PROD — mismo grafo, distinta credencial

Cómo se enchufa. En LangChain la integración es directa: langchain-mcp-adapters (MultiServerMCPClient) expone cada herramienta del servidor como tool nativa, con su schema. El loop ReAct de los especialistas no cambia — cambia el origen del dato. El reparto por agente: comercial suma identidad operativa, saldo de hoy, minutas, presupuesto y comercial asignado; portafolio suma comitentes + saldo (y tenencias cuando lleguen); riesgo encuentra acá el cimiento de su posición online; competencia no lo toca — solo usa data pública.

Lo que el MCP todavía no trae — decirlo temprano

Las tenencias por instrumento —el dato que motiva esta vuelta— hoy NO están entre las 34 herramientas. El saldo es plata, no títulos. Reemplazar de verdad el CSV requiere que FyO Digital exponga holdings por comitente e instrumento — la extensión natural del MCP existente, o un «MCP de posiciones» como servidor hermano. Es un pedido de producto a FyO Digital, no un desarrollo de esta carpeta, y conviene gestionarlo ya: es el ítem con más lead time. Mientras tanto, convivencia con regla: el CSV para títulos, el MCP para plata y operación — y cada dato citado con su fuente y su fecha, para que la mezcla se lea como trazabilidad y no como inconsistencia.

Gotchas que absorbe la arquitectura, no el prompt

El MCP tiene reglas propias: CUIT (entero, sin guiones) solo para comitentes y todo lo demás usa idEmpresa; rangos de fecha con tope (contratos 365 días, cupos 90); tipo_operacion obligatorio en órdenes; productos como "idMateriaPrima_idCategoria". Esas validaciones van en el wrapper de la tool —tipadas, con mensajes de error claros— para que el modelo no queme vueltas del loop descubriéndolas a prueba y error. Regla general del scaffold: lo que se puede validar en código, no se le pide al modelo.

El orden importa más que la lista

Checkpointer y LangSmith van primero porque son baratos y todo lo demás se apoya en ellos: sin persistencia no hay interrupt() ni human-in-the-loop; sin tracing no hay evals serios. El MCP va segundo: cambia el origen del dato sin tocar el loop, y el pedido de tenencias a FyO Digital hay que dispararlo temprano por lead time. El gate de riesgo va antes de cualquier canal que multiplique el volumen de propuestas. La memoria de negocio (cap. 10) puede pilotearse en paralelo porque no toca el grafo existente: se enchufa como un nodo más.

Decisión de plataforma · cerrada

No se usa Azure AI Foundry. Los agentes se modelan y orquestan con LangGraph; la API, los workers y sus dependencias se construyen como imágenes Docker. Para el piloto, Docker Compose levanta el stack completo en una VM interna: agent API, workers, PostgreSQL para checkpoints, Redis para colas/streaming y el acceso al MCP de FyO Digital. La evolución productiva conserva esos mismos contenedores y contratos, sin acoplar el diseño a una plataforma propietaria.

Secuencia objetivo · un turno esperado

«¿Qué le ofrezco a Crosetti?» — anatomía del turno

Cada paso indica qué componente lo resuelve y qué estado toca. La pregunta es real: cruza comercial (quién es), portafolio (qué tiene, qué rotar), research (con qué fuente) y riesgo (si puede).

00
Entrada con identidad. El mensaje llega por el canal (API/CLI) con thread_id del comercial. El checkpointer levanta el estado del hilo: si ayer hablaron de Crosetti, el contexto ya lo sabe.
01
Nodo memoria — retrieve. Consulta al cerebro de datos: hechos vigentes sobre el cliente mencionado (últimas interacciones, propuestas anteriores y su resultado, preferencias declaradas) → bloque de contexto compacto que se inyecta al supervisor.La memoria no reemplaza a las skills: la data dura (tenencias, scores) sigue viniendo en vivo. El grafo aporta lo que las skills no tienen — historia y vigencia.
02
Supervisor decide. Con conversación + memoria + hallazgos, structured output: delegar o finalizar. Detecta que necesita identidad → tenencias → view → propuesta.
03
Delegación — paralela si es independiente. Identidad y pulso de mercado no dependen entre sí → Send a comercial y research a la vez. Tenencias → rotación sí es cadena → en serie.
04
Especialistas ejecutan. Cada ReAct corre sus tools según el reparto del capítulo 05: skills locales para scores y research, MCP FyO Digital para saldo de hoy, minutas y comercial asignado (tenencias por instrumento aún del CSV, hasta la extensión). Portafolio arma la propuesta y valida números contra research — el atajo local ya apagado: la view llega por handoff con fuente+fecha.
05
Gate de riesgo. La propuesta pasa por el nodo riesgo ANTES de sintetizarse: suitability contra arquetipo, concentración resultante, apalancamiento. No pasa → vuelve a portafolio con el motivo; portafolio propone la alternativa que sí entra. Máximo un ciclo de reintento.
06
Confirmación humana donde toca. Si la acción es sensible (mensaje listo para mandar, excepción de límite), interrupt(): el grafo se pausa con estado persistido y espera el OK del comercial. Gracias al checkpointer, puede esperar horas.
07
Síntesis. Respuesta única: qué tiene, qué se propone y por qué, cada número con fuente+fecha, el veredicto de riesgo visible, y qué decide el humano claramente separado de qué sugiere el sistema.
08
Persistencia. Checkpoint del hilo actualizado + el turno completo escrito al cerebro como episodio: se dijo esto, se propuso aquello, riesgo observó tal cosa.
09
Aprendizaje. Cuando el comercial marca el resultado (llamó / no llamó, aceptó / rechazó), ese hecho entra al grafo como relación con fecha. En seis meses, «qué propuestas funcionan con este perfil» es una consulta, no una intuición.

    Dónde vive el estado

    Hoy, todo el estado del sistema es el SupervisorState: messages, next_agent, task, findings[], trace[], delegations — y muere con el proceso. El esperado suma tres campos y una propiedad: el bloque de memoria (retrieve), la propuesta tipada (para que el gate audite un objeto, no un texto), el veredicto de riesgo — y todo checkpointeado por thread_id, para que un interrupt() pueda esperar horas sin perder nada.

    El loop del juez

    Los evals no son un examen de una vez: cada trace real de LangSmith que falle en producción se convierte en caso del dataset, y el spot-check humano semanal calibra al judge (¿está aprobando cosas que un comercial rechazaría?). En seis meses el dataset dorado deja de ser sintético: es la historia real del sistema, curada. Es el mismo principio del cerebro de datos (cap. 10), aplicado a la calidad.

    Ahora, técnico: cómo se cablea esto en LangGraph. El sistema ya tiene los dos ganchos que un harness de evals necesita: el trace[] del estado (cada delegación y tool call quedan registradas — trajectory evals gratis) y el ruteo tipado (la decisión del supervisor es un objeto Pydantic testeable con pytest, sin tocar la red). Sobre eso se montan cuatro niveles de eval, del más barato al más caro:

    Harness de evals · LangSmith evaluate() sobre el grafo real # dataset dorado: PROBAR.md + sintéticos por regla dura
    from langsmith import Client, evaluate
    client = Client()

    def correr(inputs):  # target = el grafo compilado, no un mock
        out = build_agent("supervisor").invoke({"messages": [("user", inputs["pregunta"])]})
        return {"respuesta": out["messages"][-1].content, "trace": out.get("trace", [])}

    def ruteo_correcto(outputs, reference_outputs):  # nivel 2: trajectory eval sobre trace[]
        delegs = [t["agent"] for t in outputs["trace"] if t["type"] == "delegation"]
        return {"key": "ruteo", "score": delegs[:1] == reference_outputs["primera_delegacion"]}

    def grounded(outputs):  # nivel 1: assertion — número sin (fuente fecha) = falla
        nums  = re.findall(r"\d+[.,]?\d*\s*%|TNA|TIR", outputs["respuesta"])
        citas = re.findall(r"\((view FyO|Delphos|Mesa Granos)[^)]*\d{2}/\d{2}\)", outputs["respuesta"])
        return {"key": "grounded", "score": (not nums) or bool(citas)}

    evaluate(correr, data="fyo-golden-v1", evaluators=[ruteo_correcto, grounded],
             experiment_prefix="supervisor-sonnet5")  # A/B de modelos = mismo dataset, otro prefix

    Nivel 1 — unit por nodo: supervisor_node se invoca con estados sintéticos y se asserta la SupervisorDecision (pytest puro). Nivel 2 — trajectory: se corre el grafo entero y se compara trace[] contra la trayectoria de referencia: agente correcto, orden correcto, sin delegaciones repetidas. Nivel 3 — judge: LLM-as-judge (Opus 5) con rúbrica sobre la respuesta final. Nivel 4 — online: los traces de producción reciben create_feedback cuando el comercial marca el resultado — y ese es exactamente el gancho del loop de aprendizaje.

    Aprendizaje · el loop de recompensa esperado

    RL sin fine-tuning: dónde aprende de verdad

    Claude por API no se fine-tunea: no hay PPO ni DPO sobre el modelo. El «RL» honesto de este sistema es un loop de recompensa sobre las piezas ajustables alrededor del modelo — que es donde, en la práctica, vive casi toda la mejora de un sistema agéntico.

    01
    La señal de recompensa. Cada propuesta emitida queda atada a su run_id de LangSmith. Cuando el comercial marca el resultado (aceptó / rechazó / ejecutó), entra como create_feedback al trace y como arista RESULTÓ al grafo de conocimiento. Reward = f(aceptación, resultado a 30 días).Sin esta señal no hay RL de ningún tipo — por eso el loop de captura va en Fase 1, aunque lo que aprende llegue después.
    02
    Política 1 — los pesos del NBA. El ranking «a quién llamo hoy» es una política paramétrica: con el log (contexto del cliente, acción propuesta, reward) los pesos se re-estiman offline como bandit contextual. Es scikit-learn sobre el histórico, no GPU — y es el RL con mejor retorno del sistema.
    03
    Política 2 — few-shot dinámico. Las trayectorias con reward alto se guardan en el Store de LangGraph y el nodo del especialista recupera los k mejores ejemplos por similitud de contexto para inyectarlos al prompt. In-context learning: el «RL barato» de los sistemas LLM — mejora la política sin tocar un peso del modelo.
    04
    Política 3 — umbrales y sustitutos. Los umbrales del gate de riesgo y los mapas de sustitutos se recalibran con el resultado real (la mora, el post-mortem de riesgo). El principio «que aprenda» aplicado al control, no solo a la oferta.
    05
    Política 4 — la elección de modelo. Los experiments de LangSmith (mismo dataset dorado, otro experiment_prefix) más el reward online deciden cada upgrade/downgrade de modelo por nodo. Sonnet vs. Opus en portafolio se resuelve con datos, no con intuición.
    Guardrail del reward: se optimiza aceptación + resultado del CLIENTE — nunca comisión del agente. Si el reward huele a revenue, el principio 03 muere y la adopción con él.

    10Segunda instancia · memoria

    El cerebro de datos: Zep Cloud y Graphiti

    Hoy el sistema es amnésico: cada corrida arranca de cero y la «vigencia» de una view vive en un campo fecha que alguien tiene que mirar. El cerebro de datos es un knowledge graph temporal: hechos con fecha de validez e invalidación, consultables por cualquier agente.

    Graphiti es el motor open source de Zep (repo getzep/graphiti, Python) para construir knowledge graphs temporales: le das episodios —mensajes, JSON, texto— y extrae entidades y relaciones con un LLM, guardándolas como aristas bi-temporales: cuándo ocurrió el hecho y cuándo lo supimos, con valid_at / invalid_at. Cuando llega un hecho que contradice uno anterior, el viejo no se borra: se invalida — la historia queda. La búsqueda es híbrida (embeddings + BM25 + recorrido del grafo) y de baja latencia, y la ontología se define a medida con modelos Pydantic. Corre sobre Neo4j o FalkorDB, en infraestructura propia, operado por nosotros.

    Zep Cloud es el servicio gestionado construido sobre Graphiti: API de memoria con usuarios, threads y episodios, un grafo por usuario más grafos compartidos de grupo, y un context block ya armado para inyectar al prompt. SDK Python e integración directa con LangGraph. Cero operación — a cambio, los datos viajan a un cloud de terceros.

    Por qué un grafo temporal y no otro vector store: nuestra información pierde vigencia — es su característica definitoria. La view «BULLISH AL30 (view FyO 17/07)» puede estar invalidada por la view del 24/07. Un RAG vectorial devuelve ambos chunks con score parecido y le deja el problema al prompt; el grafo temporal marca la primera como invalidada por la segunda y conserva ambas. El mismo patrón sirve para límites de riesgo que cambian, tenencias que rotan, y relaciones comerciales que se enfrían. La regla dura de los agentes —todo con fuente+fecha— deja de ser una instrucción y pasa a ser la estructura del dato.

    Qué es memoria y qué no — la frontera con las skills

    El grafo NO reemplaza las fuentes vivas. Tenencias, saldos, scores NBA y perfiles siguen llegando por skills y por el MCP FyO Digital en tiempo real: son la foto de hoy y ya tienen dueño (cap. 05). Al grafo va lo que esas fuentes no tienen: lo temporal y lo relacional — views con vigencia, interacciones con el cliente, propuestas y sus resultados, límites y excepciones. Si un dato tiene sistema de origen, el grafo lo referencia (idEmpresa, id_grupo, ticker); no lo duplica como fuente de verdad.

El cerebro de negocio es compartido: views, clientes, propuestas, límites — un grafo de grupo (o un Graphiti común) que todos los agentes leen con la misma vista. Confundirlas es un error de diseño: lo que un comercial le contó al sistema sobre su interna no es un hecho del negocio.

    Integración · cuándo prende la memoria esperado

    Cómo se enchufa al grafo LangGraph

    Cuatro puntos de contacto, todos incrementales — ninguno toca los especialistas existentes.

    01
    Retrieve al abrir el turno. Nodo antes del supervisor: busca en el grafo por las entidades del mensaje (cliente, tickers) y arma el bloque de contexto — hechos vigentes primero, invalidados solo si se piden. En Zep, es el context block del thread; en Graphiti, una búsqueda híbrida centrada en el nodo del cliente.
    02
    Tool de memoria para especialistas. memoria_cliente(id_grupo) como tool: el comercial la usa para el briefing («última interacción, propuestas previas y qué pasó»), portafolio para no re-proponer lo rechazado hace dos semanas.
    03
    Write al cerrar el turno. Después del finish, async para no sumar latencia: el turno entra como episodio y el motor extrae entidades y relaciones. Las propuestas emitidas se escriben explícitas, no se dejan a la extracción.
    04
    Ingesta fuera de línea. Jobs que alimentan el cerebro sin conversación de por medio: view_mercado.json nueva → episodios JSON (cada view nueva invalida la anterior del mismo ticker); minutas del MCP (obtener_minutas) y debriefs → episodios de interacción; resultado de propuestas → aristas de aprendizaje.Este job es el que convierte «estructurar el research» —el faltante del doc conceptual— en un pipeline concreto. Y con las minutas viniendo del MCP, el grafo de relación se llena solo: la arista CONTACTÓ sale del CRM, no de la buena voluntad de cargarla dos veces.
    La memoria prende cuando
    • Se abre un turno y hay entidades conocidas → retrieve
    • Un briefing necesita historia → tool memoria_cliente
    • Se cierra un turno con contenido → episodio async
    • Llega research nuevo / debrief / resultado → ingesta
    No prende — no es su rol
    • Tenencias y scores del día → skills/MCP en vivo, siempre
    • Números de mercado como fuente de verdad → el corpus manda; el grafo referencia
    • Nada del grafo va al cliente final sin pasar por persona
    Criterio Zep Cloud · gestionado Graphiti self-hosted · open source
    Puesta en marchaDías: SDK + API key. Users, threads y context block resueltos.Semanas: Neo4j/FalkorDB propio + pipeline de ingesta + retrieval a medida.
    OperaciónCero — es el producto.Nuestra: base de grafos, workers de extracción, backups, upgrades.
    Residencia de datosCloud de terceros. Con nombres de clientes y posiciones de una sociedad de bolsa, exige revisión de DPA/compliance — o anonimizar con id_grupo antes de enviar.Todo queda en infraestructura propia. La opción defendible ante secreto bursátil y datos sensibles.
    Ontología customSí — entity types propios sobre la API.Sí — Pydantic, control total del modelo y del retrieval.
    CostoSuscripción por uso.Infra + LLM de extracción (cada episodio ingerido consume tokens) + horas de ingeniería.
    RiesgoLock-in de API y datos afuera.Deuda operativa; el motor es el mismo Graphiti, así que el modelo de datos es portable entre ambos.
    Recomendación — el camino de dos vías

    Pilotear con Zep Cloud, construir el cerebro con Graphiti. Vía rápida: la memoria conversacional (threads de los comerciales) en Zep Cloud con identificadores anonimizados (id_grupo, nunca nombres) — mide en semanas si la memoria mejora los briefings, sin proyecto de infraestructura. Vía definitiva: el cerebro de negocio (views, propuestas, posiciones, aprendizaje) en Graphiti self-hosted sobre Neo4j, porque esa data no debería salir de fyo. Como Zep corre Graphiti por dentro, la ontología que se valide en el piloto migra al self-hosted sin rediseño. La decisión final es de compliance tanto como de ingeniería — y conviene forzarla temprano, no descubrirla tarde.
